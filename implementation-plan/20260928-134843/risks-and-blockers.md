# Risks and Blockers

| Risk | Affected stages | Mitigation |
|---|---|---|
| Current GitHub credentials cannot prove branch rules, Actions policy, or protected-environment reviewers | STAGE-009 through STAGE-015 | Repository owner validates settings and records evidence before production activation |
| PyPI Trusted Publisher and production package ownership require external owner actions | STAGE-010, STAGE-015 | Reserve namespace early; use TestPyPI first; keep production jobs disabled until ownership is confirmed. STAGE-011 rehearsal GHCR access and visibility were verified in run `36779670844`; production activation remains gated by STAGE-015 |
| The production Ed25519 signing identity requires controlled rotation and incident handling | STAGE-013, STAGE-015 | Key `xferry-release-2026-09` is held in the required-reviewer `production-release` environment; `kgmnotes` owns rotation/revocation; only its public key is committed; STAGE-012 protected signing passed in run `36785117025`; follow the `SECURITY.md` incident runbook |
| Real arm64/systemd validation infrastructure may be unavailable or QEMU may be insufficient | STAGE-005, STAGE-006, STAGE-015 | Use native arm64 runners for final managed-host acceptance; treat QEMU as preflight only if systemd cannot be exercised faithfully. STAGE-011 native amd64/arm64 container acceptance passed in run `36779670844` |
| Local `main` is 29 commits ahead of `origin/main` and has no remote CI evidence for those commits | All stages | Push/reconcile through the normal reviewed branch process before release-environment activation |
| PyPI versions and public release assets are effectively immutable and partial publication cannot be rolled back atomically | STAGE-010 through STAGE-015 | Rehearse on TestPyPI/draft or staging assets, publish only exact candidates, never reuse a version, and define partial-release response |
| Manifest v2/state changes could strand existing managed installations | STAGE-004, STAGE-006, STAGE-007, STAGE-013 | Parse v1 read-only for migration/rollback, write v2 for new releases, and add upgrade/rollback fixtures from current state |
| A compromised publishing identity could sign malicious root-run updates | STAGE-007, STAGE-013, STAGE-015 | Required-reviewer environment, least privilege, key isolation, public key IDs, rotation/revocation, immutable artifacts, incident runbook. STAGE-012 isolated signing from secret-free publishing and read-only verification in run `36785117025` |
| The signed installer currently re-downloads and structurally validates the manifest signature after the operator's offline verification; substitution can make the installed release ineligible for later rollback but cannot authorize different installer or executable bytes | STAGE-012, STAGE-013 | Before public activation, bind the persisted envelope to the already verified release asset or verify it again through the bundled runtime; retain fail-closed installed-state admission |
| Documentation may get ahead of publicly available artifacts | STAGE-014 | Keep public commands guarded until post-publish acceptance passes; docs tests verify real names/commands and current channel state |
| Audit evidence can become stale as source changes | All stages | Each stage re-reads its source findings and runs targeted plus full verification before closure |
