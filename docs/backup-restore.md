# Cold backup and restore

Use a cold, consistent copy to recover a permanent installation. A release
rollback restores executable/configuration state; it is not a backup of user
files. Rehearse this procedure on an isolated replacement installation before
depending on it.

The offline rebind module described here ships with the next release containing
this guide. It supports snapshots captured with that release or later and an
**exactly matching recovery package**. Already published `0.3.2` packages do not
contain the module. Older archives need separately verified compatibility; do
not relabel their version file or combine recovery with an upgrade.

## What a consistent copy contains

| Installation | Copy together |
| --- | --- |
| Portable | The selected INI and any migration sidecar, its effective private-state root, the exact files folder, protected auth file, and external TLS/ACME material. Preserve the absolute configuration path: the default private-state location depends on it. |
| Managed Linux | `/etc/xferry`, `/var/lib/xferry`, the actual host files source if mounted from elsewhere, external certificate/auth files, and the installed release identity. Record the unit's `User`, `Group` and `BindPaths`. |
| Generated Docker | The deployment directory (Compose file, INI, deployment metadata and protected host auth file), the host files bind mount, and the actual volumes corresponding to `xferry-data` and `xferry-acme-state`. The `xferry-secrets` volume is regenerated by `secrets-init` from the saved protected host secret. |

The files folder includes hidden `.xferry-encrypted/` ciphertext. Private state
includes `.xferry/encrypted-uploads/` journals and
`.xferry/encrypted-storage-root`, as well as `notes/`. Preserve all of them.
Include external files referenced by the configuration even when they are not
below these default directories. Do not publish the backup directory through
xferry: it contains credentials, private keys and private note metadata.

## Capture the snapshot

1. Resolve the selected deployment and its effective paths. Record the exact
   runtime version, image digest or executable identity, configuration path,
   host-to-runtime mounts, and owners/modes. Prevent concurrent setup, update,
   configuration changes and writes by other programs sharing the files folder.
2. Create a private snapshot directory outside the files folder. Capture the
   **runtime's** version before stopping, preserving its complete output:

   ```console
   /opt/xferry/current/xferry --version > xferry-version.txt
   ```

   For portable use its installed `xferry --version`; for Docker use
   `docker compose exec -T xferry xferry --version`. The file must contain
   exactly `xferry X.Y.Z` and a newline. Keep it with the archive and checksums.
   This is operator-recorded version metadata, not a publisher attestation.
3. Stop foreground xferry with `Ctrl+C`, managed xferry with `xferry stop`, or
   Docker with `docker compose stop xferry`. Confirm that the process and its
   workers have exited. A closed listening port alone is insufficient. Keep
   external writers stopped until the copy finishes.
4. Archive every selected path once, preserving ownership, permissions, ACLs,
   xattrs and sparse files. On Linux, a GNU tar example is below. Replace the
   snapshot path and prepare `paths.list` with the real paths from the table,
   one path per line relative to `/`, with no duplicate nested trees:

   ```bash
   SNAPSHOT=/srv/xferry-backups/maintenance-snapshot
   sudo tar --create --file "$SNAPSHOT/data.tar" --directory / \
     --acls --xattrs --numeric-owner --sparse \
     --verbatim-files-from --files-from "$SNAPSHOT/paths.list"
   (cd "$SNAPSHOT" && sha256sum data.tar xferry-version.txt paths.list > SHA256SUMS)
   ```

   For Docker, obtain actual volume names with Compose inspection; copy volume
   contents with a temporary helper container while xferry is stopped, and copy
   the host files bind mount separately. Preserve numeric owners. Do not use
   `down --volumes`: that removes data. Record the exact helper/image identity
   used for the rehearsal as well as the application image digest.
5. Verify `sha256sum --check SHA256SUMS` from the snapshot directory, restrict
   archive access, and store an independent copy. Restart the original service
   only after the consistent copy has finished. Protect checksums with the
   archive; a modified archive and modified checksums are not authenticated.

## Restore before starting xferry

1. Keep the archive unchanged. Verify its checksums and recover on an isolated
   replacement installation of the **same exact version**. Do not expose it to
   user traffic or start the server yet.
2. Extract into an empty staging area and verify the selected paths, then place
   the recovered files, private state and configuration in their final
   destinations. Restore the runtime account's ownership, private modes and
   ACLs on this isolated copy. Do not recursively change ownership of an
   unrelated shared folder. Keep configuration, auth and private state outside
   the public files directory.
3. For a generated Docker deployment, restore the saved deployment directory,
   named volumes and files bind mount. Recreate its derived secret volume with
   the existing `secrets-init` service using the saved host auth file. Keep the
   recorded exact image digest selected. Do not run the xferry service yet.
4. When the snapshot contains encrypted storage, validate it with the offline
   module below **before any server startup**. Copying onto a new disk or into
   a new directory changes its device/inode identity, even if the path text is
   identical. The ordinary startup guard intentionally rejects that change.
5. Run configuration validation, start the isolated server, require
   authenticated `PING /` with `health: ready`, and verify an existing ordinary
   file's checksum, saved note ciphertext, a completed encrypted file, and a
   partial transfer if present. Also exercise one new upload/download/delete.
   Return traffic only after these checks pass. Upgrade separately afterward.

## Explicit encrypted-storage rebind

The module validates every journal and payload without constructing the runtime
storage service. Normal startup reconciles and may remove corrupt/orphan data,
so starting first is not a validation procedure. Run as the owner of the
restored private state, with all writers stopped, and only on the isolated
restored copy. There is no cross-process lock proving that another server is
offline.

For portable or native recovery, prepare a Python 3.10–3.14 virtual environment
with `xferry==VERSION`, where `VERSION` is the recorded exact release containing
the module. Native SCIE installations need this recovery Python environment;
the normal SCIE launcher is not a Python module runner. The module is included
in the wheel and container image, so a source checkout is unnecessary.

```console
python -m xferry.management.storage_rebind --state-root /var/lib/xferry --files-dir /var/lib/xferry/files --snapshot-version-file /recovery/xferry-version.txt --json
```

`--state-root` names the private runtime root containing `notes/` and `.xferry/`.
It does not name `.xferry/` itself. `--files-dir` is the final runtime path.
Prepare a service-readable copy of the non-secret version file in `/recovery`;
do not make the complete private backup readable to unrelated users.

Without `--apply` the command performs no writes and reports `verified` or
`rebind_required`. Inspect its receipt and then repeat the exact command with
`--apply`. It revalidates the entire copy before atomically replacing only the
binding with mode `0600` and syncing it. Repeating an already correct rebind is
a successful no-op. Do not move or copy the files directory again afterward.

### Native mounts

An external host folder such as `/srv/restored-share` can appear inside the
service as `/var/lib/xferry/files`. Writing the host path into the binding would
fail on the next service start. Use a transient unit with the final service's
actual `User`, `Group` and `BindPaths`; this example assumes the named paths
and recovery environment already exist:

```console
sudo systemd-run --wait --pipe --collect --property=User=xferry --property=Group=xferry --property=BindPaths=/srv/restored-share:/var/lib/xferry/files /opt/xferry-recovery/bin/python -m xferry.management.storage_rebind --state-root /var/lib/xferry --files-dir /var/lib/xferry/files --snapshot-version-file /recovery/xferry-version.txt --json
```

Repeat with `--apply` only after validation. Copy the deployment's real mount
mapping, not the example mapping, and keep the regular service stopped.

### Docker mounts

Run inside the final Compose mounts using the recorded image, without starting
dependencies or publishing ports. The metadata directory must be readable by
the configured container user:

```console
docker compose run --rm --no-deps --entrypoint python -v /recovery:/recovery:ro xferry -m xferry.management.storage_rebind --state-root /data --files-dir /data/files --snapshot-version-file /recovery/xferry-version.txt --json
```

Repeat with `--apply` after validation. Do not substitute a host-side files path
for `/data/files` in this container example.

### Validation and failures

The first version requires Linux/POSIX no-follow and directory-descriptor
operations. Other platforms fail before changing files. Private journals and
ciphertext directories must be owned by the recovery user and mode `0700`;
their regular files and binding must be single-link files with mode `0600`.
Restore ownership and permissions on the new copy before running the module.

The restored files directory itself must have the same owner/group as private
state and must not be group/world writable. A generated Docker deployment can
originally grant UID 10001 access to a host-owned folder through ACLs; that ACL
alone does not satisfy offline rebind. For recovery use a new dedicated files
directory owned by the runtime identity and normalize only that restored
directory. Preserve the original shared folder and backup unchanged.

- `partial`: verify the reserved payload size and every recorded chunk's
  SHA-256. Unacknowledged regions are not claimed as verified.
- `complete`: require all chunks and the complete payload, validating each
  recorded hash.
- `committing`: require all chunks and exactly one partial or final payload.
  The module leaves final commit reconciliation to normal startup.

Unknown schemas, unsafe links, unexpected entries, missing payloads, duplicate
partial/final payloads and failed hashes cause an error before a new binding is
written. Investigate using a new copy of the retained archive; do not delete
the binding or hand-edit sidecars to bypass a failure. Hash consistency is not
client-side AEAD authentication and does not authenticate a malicious archive.

| Exit | Meaning |
| --- | --- |
| `0` | Validated, applied, or already correct; inspect `status` for whether apply is needed. |
| `2` | Invalid arguments, unsupported platform, or snapshot/package version mismatch. |
| `3` | Missing, unsafe or corrupt snapshot. |
| `4` | Snapshot changed during validation or binding publication failed. |

`publication_uncertain` means replacement happened but its durability could
not be confirmed. Do not start the server; repeat read-only validation and
investigate the storage error. The module never rewrites payloads, salts,
nonces, MACs or timestamps. Subsequent startup still expires partial uploads
according to the configured TTL, including time spent in the backup.

## Keys and browser recovery

A server backup does not contain the Notepad client's session key. Preserving
note ciphertext cannot recover a lost key. Completed encrypted files still
need the original password. Resuming a partial browser upload additionally
needs the original file and browser IndexedDB nonce journal; server sidecars
do not replace it. Preserve the original site origin and browser state for
that recovery, or start a new upload with new keys and ID. Do not reuse old
nonces with different plaintext.

## Rehearse and record the result

From a contributor checkout, run the isolated synthetic drill:

```console
python tools/restore_drill.py --json
python -m pytest -q tests/test_storage_rebind.py tests/test_backup_restore.py
```

It accepts no target directory and operates only in its own temporary tree.
It creates real encrypted fixtures and exercises authenticated loopback HTTP,
copies cold state into a new directory, validates/rebinds it, checks ordinary
files and notes, decrypts a completed file locally, resumes a partial file and
checks a new upload/download/delete. Client keys remain only in the drill
process, and the receipt contains counts and checksums rather than credentials
or plaintext. Negative tests cover corrupt copies and publication failures.

Record a separate disposable native/Docker rehearsal with the actual unit,
runtime user, mounts, volumes and retained TLS material. Check the version and
identity, final paths, config validation, authenticated health and data checks,
then retain a redacted result with the backup procedure. The temporary-tree
drill does not verify real systemd ownership, Docker volumes or public ACME.
